# 架构说明

这份文档写给要改代码的人：数据怎么流动、每个模块负责什么、改动时哪些约定不能破。

## 一场 demo 进来之后发生了什么

1. **接收。** 网页上传走原始字节流（不用 multipart，省掉一个依赖）。后端边收边计算 SHA-256，并检查文件头：CS:GO 的老格式会直接被拒绝。如果库里已经有同样指纹的比赛，临时文件会被丢弃，直接返回已有的那场。
2. **解析。** `app/parser.py` 调用 awpy，把每个数据集（回合、击杀、伤害、射击、购买……）转成普通的字典列表。所有以 `steamid` 结尾的列都转成字符串，因为 SteamID64 超过了 JavaScript 能精确表示的整数范围。某个数据集解析失败不会让整场失败，错误会被记录下来。
3. **存原始层。** 解析结果原样压缩后存进 `datasets` 表。这一步之后，demo 本体就不再是必需品了。
4. **派生。** `app/analysis/derive.py` 从原始数据推出规范化的事实表：每回合、每人每回合、每人每场、击杀明细、武器汇总。`app/analysis/highlights.py` 在此基础上识别高光。
5. **记录溯源。** 每次解析和派生都会在 `parse_runs` 里留一条记录：用的解析器版本、awpy 版本、文件指纹、各数据集行数、耗时和告警。导入成功、失败或重复都会写进 `import_log`。

之后所有的统计、趋势、规则发现都只读派生层，全部用 SQL 完成。

## 模块分工

- `app/main.py`：创建 FastAPI 应用、挂载路由和静态文件、本机访问保护、启动入口。`create_app()` 接受配置和解析函数作为参数，测试就是靠这一点换成合成数据的。
- `app/config.py`：所有路径和环境变量集中在这里。
- `app/api/`：HTTP 路由，按领域分成比赛、玩家（跨场）、导入、系统四个文件。路由里尽量不写业务逻辑。
- `app/ingest.py`：导入流水线（指纹、去重、解析、存储、派生），以及「按存档重算」和「用 demo 重解析」。它不依赖 Web 框架，可以直接在脚本和测试里调用。
- `app/store.py`：SQLite 存储和结构迁移。
- `app/analysis/`：纯计算，不碰数据库。`common.py` 放阵营归一和「tick 属于哪个回合」，`derive.py` 做阵营推断和事实表，`metrics.py` 放 Rating 近似公式和多杀，`highlights.py` 识别高光，`insights.py` 是规则发现引擎，`narrate.py` 是 AI 叙述层。
- `app/services/`：`stats.py` 是跨场聚合的 SQL，`scan.py` 负责找本机的 Steam 录像目录。
- `app/jobs.py`：后台任务队列（两个线程），任务进度只存在内存里。
- `app/replay.py`：按需从 demo 解码某个回合的走位，压缩后缓存到磁盘。
- `app/devtools/synth.py`：合成比赛生成器，测试和界面预览都用它。
- `app/static/`：前端。没有构建步骤，`js/` 下的文件用普通 `<script>` 按顺序加载、共享全局作用域：`core.js` 是公共层，其余每个文件对应一个页面，最后由 `boot.js` 启动。

## 阵营推断为什么要自己做

awpy 的 `players` 数据集里每个人只有一个 `side`，是「最后一次观测到的阵营」。半场换边以后，这个值对一半的回合都是错的，不能拿来做分阵营统计，也不能拿来判断胜负。

`derive.py` 的做法是：先把击杀、伤害、购买、开火、致盲这些带 (玩家, 阵营, tick) 的记录按 tick 归到回合里，对每个 (玩家, 回合) 投票取多数；再根据「两个人在共同回合里是否总是同一边」把十个人分成两队；最后每个回合用全队的观测给队伍投票，得到队伍在这一回合的阵营。玩家的阵营一律取所在队伍的阵营，这样换边瞬间偶尔出现的脏记录会被多数票吸收掉。

回合归属用的是 `official_end_tick` 而不是 `end_tick`：回合胜负判定之后到正式结束之间仍然可能有击杀。最后一回合没有 `official_end_tick`，退回 `end_tick`。

## 数据库

原始层是 `matches`（每场一行，含文件指纹、版本号、队伍比分、demo 状态）和 `datasets`（每场每个数据集一行，zlib 压缩的 JSON）。

派生层是 `rounds`、`player_match`、`player_round`、`kills`、`player_weapon`、`highlights`。`player_round` 是分阵营统计的真正来源，每人每回合一行。

辅助表有 `parse_runs`（解析溯源）、`import_log`（导入记录）、`app_settings`（AI 与数据管理设置）、`reports`（生成过的复盘，带模型名和版本号）、`schema_meta`（结构版本）。

用 sqlite3 命令行就能直接回答问题，比如某个账号在 mirage 打 CT 的 ADR：

```sql
SELECT SUM(pr.damage) * 1.0 / COUNT(*) AS adr, COUNT(*) AS rounds
FROM player_round pr JOIN matches m ON m.id = pr.match_id
WHERE pr.steamid = '7656119...' AND m.map_name = 'de_mirage' AND pr.side = 'counter-terrorist';
```

## 三个版本号，什么时候改

- `store.SCHEMA_VERSION`：数据库结构变了就加一，并在 `MIGRATIONS` 里写一个迁移函数。迁移必须能在旧库上安全执行；有数据的旧库升级前会自动备份。
- `derive.DERIVE_VERSION`：派生口径变了（新指标、修正算法、高光规则调整）就加一。程序启动时会发现口径过期的比赛，在后台用存档的原始数据重算，用户什么都不用做。
- `parser.PARSER_VERSION`：解析产物的形状变了（新增数据集、列的含义变化）就加一。旧比赛不会自动重解析（那需要 demo 本体），只会在设置页提示「有 N 场可以重解析」。

判断标准很简单：只改了计算方式，就动 `DERIVE_VERSION`；改了从 demo 里取什么，就动 `PARSER_VERSION`；改了表结构，就动 `SCHEMA_VERSION`。

## 加一个新指标的步骤

1. 在 `derive.py` 里算出来，写进对应的事实表（需要新列的话同时加迁移和 `SCHEMA_VERSION`）。
2. 在 `app/devtools/synth.py` 的标准答案里补上这个量，并在 `tests/test_derive.py` 里加断言。
3. 把 `DERIVE_VERSION` 加一，老比赛会自动重算。
4. 在 `services/stats.py` 里加聚合，在前端展示。

## 换解析器

awpy 只在 `app/parser.py` 和 `app/replay.py` 里被用到。换成别的解析器，只需要写一个返回同样形状 `{meta, header, datasets, timings, dataset_errors}` 的 `parse()`。`parser.EXPECTED_COLUMNS` 列出了派生层依赖的列，缺列会在解析记录里产生告警，而不是悄悄算出 0。

## 几条不能破的约定

- 后端只监听 `127.0.0.1`，并校验 Host 头（防 DNS 重绑定）和写请求的 Origin（防别的网站跨站调用）。
- steamid 在全链路都是字符串。
- 前端零构建链、零 CDN、零框架。
- 程序永远不删除不在 `数据/demos/` 里的文件，也就是说 Steam 目录里的原始录像绝对不会被动。
- 「样本不足就不下结论」：任何新的分析规则都要先检查样本量。
